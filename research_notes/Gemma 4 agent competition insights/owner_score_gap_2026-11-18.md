## 3. Where your agent loses solves

### Most failures occur after an edit exists

Your sequential, four-L4 timing run recorded **129 tasks, 118 nonempty patches and 34 solves**. Assuming each solve requires a nonempty patch, the pass rate decomposes as

$$
P(\mathrm{solve})=P(\mathrm{patch})P(\mathrm{solve}\mid\mathrm{patch})
=\frac{118}{129}\frac{34}{118}=26.36\%.
$$

There were **11 empty outputs and 84 nonempty failures**. Even an oracle that made all 11 empty cases correct while leaving every other decision alone would gain at most 8.53 points on this cohort. Converting those 11 to patches of average observed quality would gain roughly three solves. The 84 failed patches are a much larger pool, although some are blocked by the local verifier. An explicit submit call is a particularly weak stand-in for a solve because the harness automatically extracts a nonempty working-tree diff at task termination. [Your four-L4 timing and resolution record](https://github.com/Shengboj0324/Gemma-4-Agentic-Platform/blob/3ba667449cffbd5da03608671897efe60da80f65/docs/45-campaign-plan.md#L499) · [Official harness, patch extraction and grading](https://www.kaggle.com/competitions/gemma-4-developer-agent/data)

Across four earlier v2 runs, your campaign attributed approximately **56% of 354 nonresolving patched attempts to assertions** and **34% to missing dependencies**. Successful attempts reached their first edit at call four versus call nine on failures, and ran a test more often (42% versus 18%). These are correlations with task difficulty. Forcing the first edit earlier on a poorly understood task can produce an early *wrong* patch. The question is whether the agent’s first test distinguishes a correct implementation from its current wrong one.

## 5. Experiments I would run, in order

### First — distinguish a wrong behavioral hypothesis from an incomplete implementation

Freeze the scored v2 bundle. On the 17 small and medium consistent misses above, inspect each first source edit and the next observation. Re-grade the saved extracted diff under the same evaluator. Assign one primary failure per issue using evidence that could change the decision: wrong code path, right path but wrong behavior, partial propagation, missing new file or export, or an uninterpretable verification result. For each, record the cheapest observation available to the live agent that would have distinguished the wrong patch from a correct one. Record “unknown” when the trace cannot establish it. Use the reference diff, changed-file labels and grading tests **only for retrospective evaluation**. The agent must act from the issue, repository and its permitted outputs.

Then run one controlled policy replacement. Replace the existing fixed verification paragraph with this decision rule in substance: after the first production edit, check the smallest observable behavior that distinguishes the issue’s expected result from the old behavior. If the assertion directly contradicts the change, revise once and rerun. If the check cannot run because a fixture is missing, use a small public-entry-point example if available, otherwise inspect the diff and finish. When the issue explicitly requires two entry points or names a caller and callee, inspect that boundary before finishing. Keep the rest of v2 and its six-tool interface fixed. Your v2 already asks for exact names and parallel implementations. The new variable is **what evidence triggers another edit and what ends the task**. The v25/v30 control argues against adding a general completeness checklist.

For each candidate-only solve, ask what the new observation exposed. For each lost solve, check which extra step displaced a correct action or changed an already-correct patch. The success criterion is the paired full-task result on fresh repositories. Reduced time to first edit, more tests run and more nonempty diffs are secondary measurements. [Existing call plan](https://github.com/Shengboj0324/Gemma-4-Agentic-Platform/blob/3ba667449cffbd5da03608671897efe60da80f65/configs/variants/callplan-v1.md) · [Existing paired evaluator](https://github.com/Shengboj0324/Gemma-4-Agentic-Platform/blob/3ba667449cffbd5da03608671897efe60da80f65/zenithsync/paired_eval.py)

### Second — give cross-file changes a bounded alternative to the fixed call schedule

Try this only if the trace audit finds repeated partial-propagation failures. Trigger an extra inspection on evidence available before grading, such as a changed public signature with independently found callers, or an issue describing the same behavior at two entry points. Spend one targeted search and one bounded read on that dependency. Require the check to name an actual caller, re-export or parallel implementation. Return to ordinary v2 when the condition is absent. The intended saving is on one-file issues, where v2 is substantially stronger. Measure how often the trigger mistakenly spends extra calls on those cases. Log trigger frequency, how often the extra file mattered, additional wall time, and final wins/losses on triggered **and untriggered** tasks.

A simple break-even calculation helps decide whether a router merits a full evaluation. If a fraction $q$ of tasks is routed, the conditional paired gain on that set is $g$, and the rest experience a conditional loss $h$, the net gain is $qg-(1-q)h$. At hypothetical $q=0.25$ and $h=0$, this branch alone would need a **34.5-point conditional improvement** to supply the whole 5/58 public gap. At $h=0.02$, it needs about **40.5 points**. Those are illustrative requirements. They explain why a targeted specialist can be valuable while still requiring an independent gain on common tasks. Do not estimate $q$ on hidden tasks from public reference patch sizes.

### Third — confirm transfer and runtime before making a competition decision

1. **Use two evaluations with distinct jobs.** Keep the 129-task score over its full denominator for comparison with your history. Also report the frozen gold-valid, empty-fails cohort for diagnosis, with a record of the harness version and dependency order. The host’s hidden repositories are disjoint. For confirmation, draw previously untouched repository groups from your reserved cohort, use matching gold/empty controls, and freeze the task list and budgets before seeing candidate results. Your 135-task external development rollouts and their admitted training histories are development material. Your repository already tracks a separate confirmation cohort. [Campaign and cohort history](https://github.com/Shengboj0324/Gemma-4-Agentic-Platform/blob/3ba667449cffbd5da03608671897efe60da80f65/docs/45-campaign-plan.md) · [Host confirmation](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/747248#3535945)
2. **Measure net solves and their concentration.** Run the same baseline and challenger on the same tasks, with repeated draws where affordable. Report wins, losses, ties, time, patch presence and stage of failure. Your existing gate estimates a roughly 7–9% false-pass probability for a two-run summed net of at least six under its modeled local null. Keep that preregistered rule for continuity. A candidate barely clearing it has earned an external test. It has not demonstrated a 5/58 gain on the leaderboard. A gain concentrated in one repository needs another repository-disjoint check. [Gate calibration and limits](https://github.com/Shengboj0324/Gemma-4-Agentic-Platform/blob/3ba667449cffbd5da03608671897efe60da80f65/research_notes/gate_calibration.md)
3. **Price the complete run.** With 120 sequential tasks in 12 hours, the gross allowance is 360 seconds per task including setup, before accounting for fixed overhead. Your tested projection is about 311 seconds per task, leaving roughly 49 seconds of average headroom under that extrapolation. At 1.20× the measured projection a candidate would take about 12.5 hours.
